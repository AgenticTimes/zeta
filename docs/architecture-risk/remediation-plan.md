## 一、P0 测量批（先做，1~2 批，不动生产代码）

### P0-a　R6：证明子门不会静默 0 命中
- **动作**：故意让 `tools/run_all.sh` 的一个子门 glob 失配，跑一次看 job 是否仍绿。
- **为什么排最前**：若答案是"仍绿"，则**后面每一条修复的验收门都是假的**，全部工作的证据基础失效。这是唯一一条会改变其他所有条目可信度的检查。
- **成本**：一次本地跑。
- **验收**：0 命中 → 非零退出；若已如此，本条转为"记录为已验证"。
- 对应 S6 / A4。

### P0-b　R2：未支持构造三分类
- **动作**：造 10~20 个含未实现构造的最小输入，跑 `zetac`，按 **诊断 / 静默错值 / panic** 三分类计数，落 `docs/architecture-risk/r2-inventory.tsv`（沿用 `tools/*_inventory.sh` 的既有形制）。
- **为什么**：这一条给出 R2 的真实损害量，直接决定 R1 拆分是按"兜底臂密度"还是按"实测错值热点"来切。项目已有同类工具（`junk_swallow_inventory.sh`、`empty_stmt_inventory.sh`、`truncation_inventory.sh`），形制现成。
- **成本**：1 批。
- **验收**：表里每行带输入路径 + 实测输出；`静默错值 > 0` 则 R2 升为最高优先。
- 对应 S2。

### P0-c　A3：ABI 名字瀑布复核
- **动作**：定位 09-19 文档所称"codegen 310 行名字瀑布 + C 运行时 66 条 `.set` 别名"，重测行号与计数（该文档已被实测推翻两次，见 R8，其 #1 结论不可直接引用）。
- **为什么**：若成立，它可能比 R1 更该先修——批次 406 的"整程序链接失败"就属于这一类。
- **成本**：只读，1 批内完成。
- **验收**：给出可重跑命令，不给出无口径的精确整数。
- 对应 §四 A3。

## 二、P1 结构性拆分红利（有实测损害量支撑，但要 P0-b 决定切法）

### P1　把 `lower_expr` 从 10,371 行单函数拆成按构造分派
- **现状**：`gen.rs:3527-13898` 一个函数；`gen.rs` = 14,644 行 / 全仓本月净增 72%；`MirGen` 45 字段 + 15 个 `with_*` setter。
- **动作**：按 AST 变体把 lowering 拆到 `middle/mir/lower/{expr,stmt,call,index,...}.rs`，`MirGen` 的 45 字段收成一个显式 `LowerCtx`（跨模块只读 + 显式可变子集）。**逐变体搬，每搬一个跑一次 `run_all.sh` 全量比对**。
- **顺序约束**：必须在 P0-b 之后——错值热点决定了先搬哪几条臂；也需要 P0-a 保证比对门可信。
- **不要做**：不要顺手改任何 lowering 语义。搬迁批与修复批严格分开，否则 `run_all.sh` 的 diff 无法归因。
- **成本**：多批；这是本计划里最贵的一条。
- **验收**：`wc -l src/middle/mir/gen.rs` 显著下降；新增构造 commit 不再触碰 `gen.rs`（S1）；期间 804 例夹具零回归。
- 对应 R1 / S1。

## 三、P2 独立可做、成本低、直接减损害

### P2　codegen 引入错误传播通道
- **动作**：`codegen.rs` 从"最热的一批 `fn` 的 `.unwrap()`"开始改 `Result<_, CodegenDiagnostic>`，让"符号解析不出"这类已知失败模式（批次 406）冒泡成诊断而非 panic。不必一次改完 53 个函数。

- **验收**：`codegen.rs` 的 `-> Result<` 从 0 起增、生产 `.unwrap()` 从 507 下降；新增一条"故意坏输入不 panic"集成测试。

### P4　断掉 `frontend → middle` 的 5 条反向边

- **验收**：`grep -rn 'use crate::middle' src/frontend --include='*.rs'` 为空（S4）。

### P6　文档断言改为可重跑

### P6-b　把 `check` job 挪到托管 runner
- **动作**：`check`（`cargo check`/`clippy -D warnings`/`fmt`，`ci.yml:16-25`）不依赖 x86-64 WSL2 也不依赖 `.z` 语料，改成 `runs-on: ubuntu-latest` 即可。`test` 若含 `cargo build --release` 的链接假设需先确认（本次未测）。
- **为什么**：这是全仓**唯一**能一条改动降低"整条验证面单点"的动作，且成本近乎零——它不需要新增机器、不需要新授权，只是把不依赖那台机器的 job 挪走。挪走后，那台机器停时至少编译与 lint 仍会红。
- **成本**：一次 workflow 编辑 + 一次 CI 观察。
- **验收**：`grep -c 'runs-on' ci.yml` 中出现第二种标签，且 `check` job 在托管 runner 上绿。
- 对应 R6 / S5。

## 五、明确不建议动的

- `gen_from_registry.py --emit` + `git diff --exit-code`（`ci.yml:75-86`）和 registry ↔ `.o` 的 `nm --check`（`:86`）：全仓最好的护栏，照抄它的形制去保护其他边，而不是绕开它。
- `clippy -D warnings`、`cargo fmt --check`：无争议。
- `selfhost_compile.sh` 的"钉住 4 例、反而通过则失败"机制：这正是 P0-a 想要的语义，应推广到 `run_all.sh` 的子门，而不是新造一套。
- 逐批次回归记录的工作方式：30 天 787 commit 能维持一致性靠的就是它。

## 六、建议的开批顺序

```
P6-b（一条 workflow 编辑，可与 P0 同批走，不必等测量）
   ↓
P0-a → P0-b → P0-c      （3 个测量批，互不阻塞，可并行；产出决定后面怎么切）
   ↓
P2 + P4 + P6            （互相独立、成本低、直接减损害）
   ↓
P1                      （最贵；在门可信、热点已知后开工）
   ↓
P3 / P5 / P7            （P5 需你先裁决；P3/P7 依 P0-b 结果）
```

先跑 P0 三条 + P6-b。P0 花一个批次的量，换来的是"后面每一条修复有没有可信验收门"；P6-b 是唯一一条不必等测量、且直接消除单点的动作。
