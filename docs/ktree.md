## Zeta 当前设计（生成于 2026-09-19）

### 串讲（因果叙述，按支柱顺序阅读）

#### 总串讲

Zeta 将 Python 源码编译为原生机器码。编译流程分为五层：文本预处理、解析为抽象语法树（AST）、转换为中间表示 MIR、生成 LLVM IR、链接 C 运行时。每一层为降低实现复杂度做出了独立的简化决策。这些决策有一个共同后果：各层之间依靠函数名与类型名的字符串匹配协作，而字符串匹配无法验证语义正确性。以下五段说明各层的决策内容与遗留问题。

#### 支柱 1 前端：文本层兼容

前端同时接受两种源码：Python 与 Zeta 自身语法。前端选择不修改解析器，而是在解析前把 Python 文本重写为花括号形式：缩进转换为花括号，续行合并为单行（1.1）。两种语法共用同一套文法，因此 Python 的每个语言特性都需要在解析器中增加分支：目前有 115 处 Python 专用判断，分布在 5 个文件中（1.2）。解析产物是抽象语法树（AST，即源代码的树形结构表示）。AST 存在三项缺陷。第一，不记录源码位置（1.3.3），因此错误报告无法给出行号。第二，类型以字符串存储（1.3.2），下游必须反复解析"pd.DataFrame"这类类型字符串。第三，节点体积大且按值复制（1.3.1、1.3.4），AST 在编译流程中被完整复制四到六次。解析器还有一个行为缺陷：遇到第一个无法识别的顶层结构时停止（1.4），其后的代码被静默丢弃。AST 同时存在信息损失：函数参数默认值在解析后被丢弃，参数仅保留名称与类型两个字符串（1.3.5）。AST 的形状也不完全规则：try 语句的末尾块会被移动到函数的返回值位置（1.3.6），按常规树形编写的遍历代码无法访问该部分，批次 126 中 import 语句整段丢失即由此引起。函数定义节点有 15 个字段，宏展开与单态化代码各自复制了这份字段清单（1.3.7）。作为对照，rust-analyzer 等成熟前端为每个语法节点记录源码位置（1.3.8）；为 AST 补充位置信息已列入 advice.md 任务 C3。
想一想：缺少位置信息与结构化类型时，类型检查能发现哪几类错误？

#### 支柱 2 中端：字符串协作的代价

中端将 AST 直接转换为 MIR，中间没有其他表示层（2.1.0.4）。MIR 这一名称来自 Rustc 的同名中间表示，但结构不同：Rustc 的 MIR 是控制流图（CFG，以基本块和跳转表示执行顺序的图），Zeta 的 MIR 是嵌套语句树（2.1.2），语句只保存表达式编号，表达式本体存放在另一张表中（2.1.1）。该设计产生两个问题。第一，指令的操作符与被调用函数名都是字符串（2.1.5），编译器通过字符串比较确定调用目标，因此公共子表达式消除会把两个不同的浮点常量误判为相同（2.1.6）；优化器从未接入编译流程（3.4.5），该缺陷尚未产生实际影响。第二，类型检查有两套实现：新实现包含类型推导引擎，但字符串类型无法参与推导（2.2.1），推导失败时静默跳过；实际生效的是旧实现，它仅检查参数个数（2.2.3、2.2.4）。泛型的处理同样存在实现与名称不符：替换表被构造为恒等映射（2.4），真正的替换由代码生成阶段按位置完成。Python 标准库通过 registry.txt 数据表绑定到 C 函数符号（2.3），查表失败时会生成裸符号名，错误延迟到链接阶段才暴露。批次 141 已引入 PyDynamic 类型表示未标注的类型（2.2.5）。
想一想：若类型以结构化数据表示，两套类型检查实现能否合并为一套？

#### 支柱 3 后端：结构化生成

后端通过 LLVM 的 C API 构建 IR（3.4.2），不使用文本拼接，是五层中实现最规范的一层。LLVM IR 采用 SSA 形式（3.4.1）：每个值只被定义一次，定义后不可修改。采用 SSA 的原因在于：此前数据流分析以变量为单位，变量被重新赋值后先前结论全部失效，判断"x 是否仍等于 5"需要检查所有赋值路径（3.4.1.9、3.4.1.10）；SSA 为每次赋值引入新名字，值的有效范围等于名字的作用域，因此无需迭代求解（3.4.1.11）。该表示于 1980 年代在 IBM 提出（3.4.1.12）。LLVM 采纳 SSA 有三个工程理由：数据流信息计算一次即可被全部优化过程复用（3.4.1.14）；名字数量不受机器寄存器数量限制，寄存器分配推迟到最终阶段（3.4.1.15）；多数分析只需单次遍历（3.4.1.16）。相应代价是汇合处的 φ 指令与 mem2reg 转换（3.4.1.17）。后端曾有的符号问题已解决：符号解析从十级候选名依次尝试（3.1）改为注册表优先；汇编别名清单已改为数据文件生成（3.2，批次 130–135）；参数类型不匹配的自动转换已改为白名单告警（3.3，批次 138）。
想一想：类型转换白名单若改为默认禁止，需要先补齐哪些类型标注？

#### 支柱 4 运行时：无类型标签的值表示

C 运行时把所有值表示为 64 位整数或浮点数，值本身不携带类型信息。Vec 是一段连续内存，起始处依次存储容量与长度（4.1）；dict 是开放寻址哈希表，字符串键仅存储其内容哈希值（4.2）。异常处理不使用栈展开，而使用 setjmp/longjmp：进入 try 时记录执行位置，发生异常时跳回该位置（4.3.1）。编译期可见的控制流（break、return）使用普通跳转指令；只有运行期抛出的异常使用 longjmp（4.3.6），因此 2.1.3 的循环机制与 4.3 的跳转栈同时存在。内存回收使用 Boehm 保守垃圾回收器（4.5）：因为值不携带类型信息，回收器无法区分指针与整数，只能将所有形似指针的值按指针处理。该设计成立的前提是某些场景不被触发：并发是顺序执行的简化实现（4.4）；try 嵌套超过 64 层后异常保护失效（4.3.4）；字符串哈希碰撞会返回错误的键。批次 137 与 140 已为未实现的库函数建立显式报错机制，其余前提仍然存在。
想一想：为每个值增加类型字段需要多少额外内存，可以消除上述哪些前提？

#### 支柱 5 演进：语料驱动的验收

项目以一个真实的量化策略语料作为验收标准，每个批次完成一项任务并记录基线数据（5.1）。2026-09-19 之前，三套基线（官方套件、python_style、语料解析）只能手动执行（5.2），同一指标在不同文档中出现过五个不同数值。批次 129 与 136 建立了统一脚本与持续集成任务；此后每个批次的验收数据出自同一口径。
想一想：若基线数据可以被随意解释，如何确认某次重构未引入回归？

#### 一句话记忆

五层直通管道以字符串匹配协作；注册表、类型动态化与统一基线，是已偿还的三项主要技术债。
